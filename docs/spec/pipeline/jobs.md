# `pipeline.jobs` — 작업

라우트 `/pipeline/jobs` · 컨테이너 `page-pipeline-jobs` · 사이드바 `nav-pipeline-jobs`

**아직 껍데기다** (`README.md` "지금 상태").

## 여기 있던 것이 나갔다 (2026-08-12)

2026-08-12 까지 이 라우트에는 **브라우저 작업대**가 있었다. 스텔스 브라우저를 켜 두고 조작하며
스크립트를 맞을 때까지 다듬는 화면이다. 그것은 `studio.browser` 로 나갔다
(`../studio/browser.md`).

나간 이유는 자리가 틀렸기 때문이다. 파이프라인의 여섯은 **순서가 곧 제품**인데
(`AC-app.shell.sidebar-06`), 작업대는 어느 단계도 아니다. 여섯 안에 두는 동안 레일은 그것을
단계 중 하나라고 말하고 있었고, 그러는 사이 `작업` 이라는 이름이 약속하는 것 — **무엇이 언제
돌았나** — 은 아무 화면도 지키지 않고 있었다.

그래서 나간 것은 작업대이고 `작업` 은 남는다. 여섯의 순서도 그대로다.

## 들어와야 하는 것

등록해 둔 실행 플로우와 지금 돌고 있는 작업을 한 곳에. `README.md` "이름 규칙" 이 이미 한
화면으로 정해 두었다 — 정의(Flows)와 실행(Runs)을 두 화면으로 쪼개는 안은 IPC 계약이 생길 때
다시 본다.

- 실행 목록: 무엇이 · 언제 · 얼마나 걸려 · 어떻게 끝났나
- 한 실행의 로그와 단계별 결과 (작업대의 로그와 같은 모양이면 눈이 옮겨 붙는다)
- 다시 돌리기, 그리고 실패한 지점부터 다시 돌리기
- 예약과 트리거

## 이 화면이 내용을 가질 때 정한다

실행 기록을 **어디에 쌓는가**가 먼저다. 지금 이 앱의 저장은 워크스페이스별 JSON 파일이고
(`../../ARCHITECTURE.md`, CLAUDE.md §5), 실행 기록은 계속 늘어나는 유일한 데이터라 같은 방식이
맞는지부터 다시 봐야 한다. 보관 기간과 상한도 같은 자리에서 정해진다.

그 다음이 IPC 계약과 인수조건이다.
