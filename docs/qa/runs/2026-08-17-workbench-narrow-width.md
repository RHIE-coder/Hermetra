## 원인 — 맨 `1fr` 은 min-content 아래로 안 줄어든다

그리드 트랙 `1fr` 의 `min-width` 는 기본이 `auto` 다. 즉 **그 칸의 내용이 요구하는 최소 폭
아래로는 안 줄어든다.** 그리고 이 칸의 내용은 Monaco 인데, Monaco 는 **마지막으로 배치된
폭을 그대로 신고한다.** 그래서 넓은 창에서 한 번 배치되고 나면, 창을 좁혀도 트랙이 옛 폭을
쥐고 화면 전체가 옆으로 밀린다.

**재현에 순서가 있다.** 좁은 폭으로 곧장 열면 안 난다 — 넓게 있다가 좁혀야 난다. 처음
실측이 `+0` 으로 나와 못 잡을 뻔했고, 폭을 훑는 순서를 유저가 한 대로(넓게 → 좁게) 바꾸고
나서야 재현됐다.

후보를 하나씩 **각각 새 앱 인스턴스에서** 실측했다. 한 번 풀리면 그 상태가 유지되므로 한
프로세스 안에서 이어 재면 첫 후보 뒤로는 전부 통과로 보인다(실제로 처음에 그렇게 나왔다):

| 후보 | 1400 → 1000 결과 |
|---|---|
| 손 안 댐 | page **+376** · grid **+400** |
| 트랙을 `minmax(0,1fr)` 로 | +0 · +0 |
| 편집기 칸에 `min-w-0` | +0 · +0 |
| 파일명 입력칸을 줄어들게 | +376 · +400 (무관) |
| 브라우저 바에 `min-w-0` | +376 · +400 (무관) |

## 고친 것

```
grid-cols-[240px_1fr]  →  grid-cols-[240px_minmax(0,1fr)]
편집기 칸(flex 열)에 min-w-0
```

`minmax(0,…)` 이 뿌리이고, `min-w-0` 은 그 한 겹 아래 flex 항목이 같은 이유로 안 줄어드는
것을 막는다. 편집기 껍데기가 공용이라 웹·모바일 스크립트 화면도 같이 고쳐진다.

**넓게 보기에는 원래 이 결함이 없었다.** 그 모드는 `grid-cols-1` 을 쓰고, Tailwind 의 숫자
`grid-cols-N` 은 바로 이 이유로 이미 `minmax(0,1fr)` 이다. 우리가 손으로 쓴 트랙만 그 보호를
안 받고 있었다.

## 테스트

`CASE-studio-121` 은 **선언을 못박지 픽셀을 못박지 않는다** — happy-dom 은 그리드 배치를
계산하지 않으므로 컴포넌트 테스트가 이 결함을 픽셀로 잡을 방법이 없다. 대신 맨 `1fr` 로
되돌리면 빨간불이 되는 것을 확인했다:

```
AssertionError: expected 'grid min-h-[420px] flex-1 gap-4 grid-…' to contain 'minmax(0,1fr)'
```

한 글자면 결함이 돌아오는 종류라, 그 한 글자를 지키는 것이 이 테스트의 몫이다. 픽셀은 위
표가 든다.
