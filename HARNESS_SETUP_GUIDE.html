Harness Setup Guide

Spec → TDD → Audit, 그리고 같은 실수 반복 방지까지 — 한 페이지로 이해하는 작업 흐름.

30초 요약. 명령 5개로 작업 흐름을 정리합니다. /setup이 준비 상태를 잡고, /intake가 요구사항을 명확히 하고, /sprint가 TDD로 구현하고, /immunize가 실수를 기록하고, /sweep이 프로젝트 전반을 점검합니다. 두 개의 자동 차단 훅이 잘못된 패턴을 디스크에 닿기 전에 막습니다.

다섯 가지 명령

STEP 0

/setup

새 체크아웃에서 준비 상태 확인 & 누락된 부분 자동/대화로 채움. Idempotent.

STEP 1

/intake

요구사항을 빈틈없이 캐묻기. 사용자가 OK 할 때까지 종료 안 됨. Spec 파일 + Tasks 생성.

STEP 2

/sprint

자동 TDD 루프. testwriter → implementer → auditor. 전체 테스트가 3번 돈다.

STEP 3

/immunize

실수를 ledger에 기록. 다음 sprint들이 시작 시 강제로 읽음. Regex 등록 시 훅이 자동 차단.

STEP 4

/sweep

프로젝트 전체 감사 (수동). 장기 drift, stale spec, 사용 안 되는 ledger rule 검출.

왜 3번? sprint 안의 변경이 무관한 다른 테스트를 깨면 어디서든 잡혀야 합니다. implementer가 자기 테스트만 돌리면 회귀를 놓칠 수 있어요. 그래서 implementer가 한 번, sprint orchestrator가 다시 한 번, auditor가 마지막에 한 번 — 세 곳 모두 전체 suite.

3계층 아키텍처 — 어디가 바뀌고 어디가 안 바뀌나

LAYER 1 / UNIVERSAL CORE

어떤 프로젝트도 안 건드림

4 agents · 5 skills · 7 scripts · 2 hooks · 1 lib · ledger schema

이 파일들은 byte-identical. 복사해서 그대로 씀.

↓ reads at runtime
LAYER 2 / PROJECT CONFIG

프로젝트당 1개의 JSON

.claude/harness.config.json

commands, 어느 check를 켤지, 어느 extractor를 쓸지, 어느 파일을 가리킬지.

↓ names plugins
LAYER 3 / PLUGINS (EXTRACTORS)

필요한 것만 1-2개

.claude/extractors/tokens/<name>.mjs · .claude/extractors/i18n/<name>.mjs

디자인 시스템 / i18n 형식별 ~40줄 어댑터. getTokens() 또는 getLocaleKeys() 하나만 export.

왜 이렇게 나눴나

예전엔 check-design-tokens.mjs 한 파일에 "파일 순회" + "정규식 파싱" + "Tailwind 토큰 추출" 로직이 다 섞여 있었습니다. Tailwind 안 쓰는 프로젝트로 옮기려면 그 파일을 통째로 다시 써야 했죠. 지금은 위쪽 두 가지는 Universal에 남기고 "Tailwind 추출" 부분만 별도 plugin으로 분리. 다른 디자인 시스템 = plugin 1개 교체.

처음 설치하는 3단계

  1. HARNESS_SETUP.md를 새 프로젝트 루트에 복사.

    Claude Code 세션에서 그 파일을 열고 "이 가이드대로 하네스 설치해줘"라고 부탁.

  2. Claude가 인터뷰 → 파일 생성.

    테스트 명령, 디자인 시스템, i18n 사용 여부 등 6~10개 질문. 답변에 따라 harness.config.json + extractor 작성.

  3. npm run preflight → READY 확인.

    이후 /intake "<your first feature>"로 첫 작업 시작.

자동 차단 훅 2종

훅언제 발동무엇을 막음
design-token-guard Write/Edit가 .tsx 등 (config에 지정한 glob) tailwind config / CSS vars 등 디자인 시스템에 등록 안 된 토큰 사용
immunity-rules-guard 모든 Write/Edit (단, .md·.claude/ 제외) ledger entry에 rule: <regex>이 있는 모든 패턴

훅이 블록하면 우회하지 말고 (a) 다른 패턴 쓰거나 (b) ledger의 rule을 좁히거나 entry를 제거하세요. 우회는 ledger의 신뢰를 망가뜨립니다.

자주 묻는 것

/audit은 없나요? /sweep이 그건가요?

맞아요, /audit은 없습니다. 비슷한 두 가지가 있어요:

  • auditor agent: /sprint 안에서 자동 호출. 그 sprint의 작업물이 PR 머지할 만한지 검증. sweep 검사 5종을 모두 돌립니다.
  • /sweep: 수동 호출. 같은 검사 + 장기 drift (오래된 spec, 사용 안 되는 ledger rule) 추가 검출.

매 sprint마다 sweep 검사는 이미 자동 실행되므로 따로 /sweep을 매번 부를 필요는 없습니다. 정기 점검 (격주/월 1회) 때만 호출.

훅이 너무 자주 막아요

훅이 적절한 위반을 막는데 빈도가 잦다면 코드가 자주 ledger rule을 건드린다는 신호입니다. 두 가지 점검:

  • Rule regex가 너무 넓어서 false positive면 → /immunize로 해당 entry 수정. regex를 좁힘.
  • 실제로 같은 실수가 반복되면 → 코드 변경 패턴을 바꿔야 함. 훅이 일을 잘 하는 중.

우회 (--no-verify 류) 금지. 우회 한 번 = ledger 신뢰 0.

다른 디자인 시스템(CSS vars / Style Dictionary) 쓰는 프로젝트인데?

Extractor 한 개만 추가하면 됩니다. .claude/extractors/tokens/css-vars.mjs 같은 새 파일에 getTokens() 함수만 구현하고, harness.config.json에서 "extractor": "css-vars"로 가리키면 끝. Driver는 그대로.

다른 i18n 형식 (react-intl JSON / i18next) 쓰는데?

마찬가지로 extractor 한 개. .claude/extractors/i18n/react-intl-json.mjs에 getLocaleKeys() 구현. Config에서 이름만 변경.

Ledger entry가 너무 많아져서 부담스러워요

200개 vague entry는 20개 sharp entry보다 못합니다. /immunize 호출 전에 기존 entry를 업데이트할 수 있는지 먼저 보세요. 90일 이상 매치 안 한 rule은 /sweep이 알려주니까 정리하시면 됩니다.

Soft rollout으로 시작하고 싶어요 (block 말고 warn)

훅 두 파일에서 process.exit(2)를 process.exit(0)로 바꾸면 됩니다. stderr 메시지는 그대로 보이지만 도구는 차단 안 됨. 팀 익숙해진 후 다시 exit(2)로 복귀.

Sprint 도중 사용자 개입이 가능한가요?

SKILL은 자동 루프지만 각 단계 사이에 결과를 보고합니다. 사용자가 그 시점에 멈추거나 방향을 바꿀 수 있어요. testwriter / implementer / auditor 중 한 곳이 escalate하면 자동으로 사용자에게 결정권 넘김.

Node 18+ 외에 다른 dependency 필요한가요?

없음. 모든 스크립트가 Node stdlib만 사용. fs, path, child_process, url 정도. npm 패키지 추가 0.
